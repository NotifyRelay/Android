<a id="archive-NotifyRelay-agent-notes"></a>

# 归档 NotifyRelay Agent Note

在不抹除仍能指导工作的历史的前提下压缩活跃决策语料。对每份记录做语义判断；字数和存续时间只是发现线索，从来不是归档判据。

<a id="read-the-contracts"></a>

## 阅读约定

分类前先读 [Agent Note 规则](../../notes/README.md)、[归档说明](../../notes/archived/AGENTS.md) 与适用的活跃生命周期说明。用当前代码、配置、包文档、生成目录、更新的 Agent Note 以及入站链接，判定某项理由是否仍然拥有或约束任何东西。

<a id="check-supersession-when-adding-a-note"></a>

## 新增记录时检查取代关系

起草前先套用[创建标准](../../notes/README.md#何时需要写一份)。每份新 Agent Note 都触发一次范围受限的审计，覆盖同一决策、机制或被否决备选方案的活跃记录。撰写新记录时逐项分类完全或部分取代：在同一 PR 中归档符合条件的已实施记录，保留并互相链接部分取代或独立有用的理由，否决过时提案，删除已不再阻止一种可能错误的 rejected 记录。当新记录吸收了全部独有命题时，套用 Agent Note 合并规则；不要把已知匹配推迟到后续语料审计。

<a id="classify-by-future-value"></a>

## 按未来价值分类

套用以下按生命周期区分的结论：

- **`implemented`——删除：** 删除仅描述小型 UI 调整或纯机械变更的整份记录，并修复或移除入站链接。局部 bug 修复、性能变更、新能力以及实质性的行为或归属决策，不会仅因已实施就符合条件。本条判据在保留/归档分类之前套用。
- **`implemented`——保留活跃：** 当记录的理由、备选方案、否定性保证、持久化/协议语义、归属边界、安全规则或重新引入条件仍可能指导未来变更时，保留该记录。判断决策本身，而非其实现机制：一次机械重命名或类型抽取仍可能记录下长期有效的命名、兼容或归属规则。长度无关。
- **`implemented`——归档：** 当一项实质历史决策已完整落地、不太可能再指导未来工作，但其历史理由仍值得保存时，归档它。符合直接删除判据的记录不得归档。
- **`proposed`——永不归档：** 仍在推进的提案保持活跃；若它已不值得推进，用诚实的理由将其转为 rejected，并满足 rejected 生命周期的格式。
- **`rejected`——仅作为护栏保留：** 只有当落败提案仍是一种诱人且有分量的错误，且记录解释了它为何落败时，才保留该否决。
- **`rejected`——删除：** 当被否决的想法已过时、被取代、不再可能发生，或不太可能阻止重新争论时，删除整份记录。修复或删除入站链接。

不要为凑配额而归档。检查范围内每份记录，把同类分组在同一原则下分类，对边界情形作最佳判断，并把真正处于交界处的决策记录下来交给后续接手者。

<a id="calibrated-examples"></a>

## 经过校准的示例

这些示例设定了门槛；其中的字数说明篇幅不是判据。

删除此类已实施记录：

- 折叠后的侧边栏控制栏——533 词：已关闭的小型 UI 行为；
- issue-policy 模块归属——已完成函数搬迁与导入改接，行为不变。

保留此类已实施记录：

- 事件溯源会话——248 词：基础性权威与持久化边界；
- 单一 Harness-home 解析器——596 词：跨产品归属规则；
- 项目会话目录——628 词：持久化存储与身份策略；
- 并行 pre-push 门禁——400 词：处于交界处，但仍指导门禁排期与资源调优；
- 丢弃的图片内容块——334 词：保留到多模态支持落地，因为它写明了协同重新引入条件。

对于 rejected 记录：

- 继续合并 compaction 包拆分——426 词：合并这些包的诱惑仍然有分量；
- 删除经由工具调用流式上报 workflow 进度——972 词：其 ACP/UI 前提已过时；
- 删除丢弃 ACP 终端元数据——362 词：后续「仅自动化 ACP」的决策已解决该问题。

<a id="archive-one-implemented-triplet"></a>

## 归档一份已实施记录

1. 把 `foo.md` 从 `implemented/<kind>/` 移到 `archived/<kind>/`；归档路径中有意不含 `implemented`。
2. 不改正文。仅在两个语言文件的 `Status: implemented` 紧下方插入 `Archived: YYYY-MM-DD`，使用归档日期且两侧取同一值。
3. 为这两处只动元数据的编辑机械地重新记录伴随记录 hash。不要翻译、重排、更新事实或修复记录内的链接。既有标题标点、空行布局与语言切换栏措辞原样保留，不是归档的前提。
4. 搜索来自活跃散文的入站链接。把它们改指向当前权威；仅当有意引用历史快照时才改为归档路径；否则删除。绝不从归档记录向外校验或修复链接。
5. 运行 `pnpm run verify-archived-agent-notes --write`。其仅追加模式先证明每份既有封印仍然匹配，然后只加入新记录的 hash。随后运行常规校验。

记录封印后，永不编辑、移动、翻译、重排或删除它。归档记录仍是有效的入站链接目标，但它们是历史快照，不是当前行为的权威。

<a id="validate-and-report"></a>

## 校验并汇报

运行归档校验器的聚焦测试、`pnpm run verify-archived-agent-notes`、`pnpm run verify-all`、`pnpm run lint` 与 `git diff --check`；额外证据按改动面选择。

汇报保留的活跃已实施记录、删除或归档的已实施记录、保留/删除的 rejected 记录、如有则被否决的 proposed 记录，以及每个真正处于交界处的案例及其字数与所选结论。不要声称归档记录的外向链接有效：归档校验器有意从不检查它们。
