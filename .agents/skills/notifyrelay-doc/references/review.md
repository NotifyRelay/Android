# 评审标准

<a id="summary"></a>

## 摘要

评审文档看读者是否完成了某个结果，而不是看模板标题是否齐全。对照代码与测试校验散文，保留确切契约，让页面既对读者有用又为维护者暴露足够的实现细节。运行仓库当前的各道门禁。

<a id="newcomer-test"></a>

## 新人测试

无仓库背景的职业工程师读过三到五个互链页面后，应能回答：产品或特性做什么、如何安全地运行或使用、其状态存放在哪里、哪个组件拥有它、它如何失败、以及在哪里改它。如果读者为了发现公共流程不得不去读源码，就补上缺失的解释。如果读者不得不消化无关的内部实现，就把那些细节下沉。

<a id="evidence-review"></a>

## 证据评审

把每条实质陈述对照其最强所有者检查。名称与入口看包元数据，API 契约看公共类型与 JSDoc，行为看运行时源码，已演练的失败路径看测试，穷尽盘点看生成的清单，理由看活跃 Agent Note。绝不要把旧 README、讨论或报告当作比当前代码与测试更强的证据。

对每条操作类断言——CLI 命令、配置片段、默认值、错误消息、平台差异——证据是实际运行它，而不是读它。在当前检出上执行确切命令或挂载确切配置之后，页面才可以陈述其行为；只引用观察到的输出、告警与失败。依赖不可得密钥或网络的断言改为点明其验证所有者，而不是断言行为。对既有页面，与最新 `origin/master` 对比，并按代码重新校验过期陈述。

只在某条陈述能帮助目标读者动手、推理或避免误用时保留它。把理由、历史、测试走查、重复清单与无关的包细节移到其所有者处。

<a id="reference-example"></a>

## 参考范例

范例页演示了该格式：简短的 Summary；链接式目录；面向用户的使用节，覆盖读者能做什么与何时选用；GitHub 原生 `<details>` 折叠的开发者向设计与实现细节；Further Exploration；以及末尾的 Dev Note。以它的结构与证据标准作为范本，让每条断言落在其拥有的源码与证据上。

<a id="verification"></a>

## 校验

迭代时跑最小聚焦检查，之后跑常驻文档检查：

```sh
pnpm run test:docs
pnpm run verify-all
pnpm run verify-all
pnpm run lint
git diff --check
```

技能变更还要运行仓库的技能调用元数据检查；行对齐的文件对要比较英文与中文的物理行数。完整复读最终 diff 一次查事实完整性，一次查简洁度、导航与归属。
