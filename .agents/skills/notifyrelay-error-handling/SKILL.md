# NotifyRelay 错误处理

定义失败、失败的所有者，以及失败之后仍然成立的安全性。

<a id="typed-structured-failures"></a>

## 有类型、结构化的失败

预期内的失败需要声明的类型、稳定的判别值和与处理相关的细节。沿用所在包的既有错误约定，保留 cause，把机器身份与展示文本分开。切勿通过解析消息文本来路由处理逻辑。`assertNever` 之类的意外缺陷可以保持为普通 `Error`；遏制绝不能把它们变成成功。

<a id="catch-recover-or-stop"></a>

## 捕获、恢复或停止

对每一种失败，在所属 API 的文档中定义处理与上报的所有者、遏制方式和保证：有效不变量，缺失/部分/已提交/未知的效果，以及清理职责。后台工作同样保留这些义务。

捕获限制的是异常传播范围，不是变更。只有受影响状态的所有者才能确立安全继续。否则应停止依赖工作、丢弃无效状态或实例，或者升级上报。仅打日志不算恢复。重试要求可安全重复、可取消，并有明确的所有者；有限操作需要预算，而持续监管需要生命周期归属与可观察的降级。

<a id="localized-actionable-visible-reports"></a>

## 本地化、可操作、可见的报告

每份最终报告都需要可读的摘要、受影响的操作和安全的下一个动作。存在接收方应用的 locale 机制时，通过它做本地化；其他诊断沿用其既有输出语言。用户可见文本中不得出现敏感的内部细节。

不受信任的状态或未知的结果必须通过 UI 或默认开启、可访问的日志可见：报告影响、不确定性、系统处置与安全下一步。持续存在的无效状态需要持续可见。没有保证时，绝不宣称成功、回滚或可安全重试。上报失败需要独立的兜底。

验证结果状态与可见结果，而不只是验证异常被捕获。

<a id="foundations"></a>

## 基础

Meyer 的 *Object-Oriented Software Construction*（1997）：契约与不变量；Sutter 的 *Exceptional C++*（1999）：异常安全保证；Armstrong 的[论文](https://www.erlang.org/download/armstrong_thesis_2003.pdf)（2003）：隔离与监管。
