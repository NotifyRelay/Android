# 发现 NotifyRelay 中的简化

找出那些能移除长期维护义务的改动：API、表示、生命周期状态、配置路径、依赖、测试或文档。宁可给出少数几个证据充分的候选，也不要追求删除数量。这是指引，不是检查清单；遵守用户给定的范围，并区分「调研」与「获准实施方案」。

<a id="establish-scope-and-constraints"></a>

## 确立范围与约束

判定各个包之前，先读 `AGENTS.md` 与架构说明，以及本仓库自己的缺陷类别规则页与测试策略页。有意的决策查相关活跃 Agent Note；新增记录用[记录规则](../../notes/README.md)。归档记录是历史示例，不是当前权威：绝不检查、校验或修复它们的出站链接。

受保护的设计是有意保留的：提议删除某条接缝、适配器或持久化提供方之前，先确认支撑它的约束仍然成立；除非用户明确推翻该约束，不要提议删除。受保护设计中的未使用成员仍是候选，只要删除它们能保住该设计的目的。

面对宽泛请求，把相互独立的领域分给子代理：按子系统、装配层、运行时接口、子进程边界与工具链切分。给每个代理一个有界领域，并要求提供消费方证据与被否决的替代方案。既要检查显眼的无用符号，也要检查体量可观的生产机制；不要在第一个看似可删的点上就停下。

<a id="search-for-removable-obligations"></a>

## 寻找可移除的义务

用下面这些问题引导发现。它们示范的是有待证伪的假设，不是当前的删除清单；每个候选都要拿消费方证据校准。

- **声明的特性是否有完整的效果路径？** 追踪生产者、变换、提供方或端点支持，以及可观察结果。一个到处被复制的字段，可能仍然没有 setter、没有读取方，或只有拒绝它的实现。除了调用方，还要搜索构造函数与判别值发出点。
- **哪些区分会改变消费方的动作？** 若干内部状态可能只需要一个面向模型的状态或一个可用标识符。保留控制授权、驻留、持久性或归属的内部区分；删除只招致无法使用的选择的公开区分。
- **更小的显式行为能否移除整个子系统？** 固定间隔、调用方提供的时区，或上报激活失败，可以消除通用日历、持久化默认值或自动回滚。要写明放弃了哪项能力、删除了哪些机制。有生产调用方时，这就是一个行为决策，而不是自动否决；实现必须留在用户授权范围内。
- **消费方能否在需要时读到权威值？** 寻找被复制的历史、晋升台账、失效事件后跟读取、以及共享投影流旁边的特性缓存。推导或复用可能一并删除订阅、保留数据、过期响应处理与恢复路径。先确定要求的观察时点。
- **是否把组合误当成了策略？** 可选服务的存在、某个提供方方法，或一个同级工具，都能表达可用性而不决定部署行为。显式配置或调用方意图操作可能移除注册表与依赖检查。当它们的归属或完成时序不同时，保留彼此独立的操作。
- **谁承担全部维护成本？** 追踪直通配置、重复的应用树、被产品使用的演示启动器、仅做解析的工作区，以及自带升级生命周期的安装辅助工具。把整个被移除的系统与替代方案对比，包括残余胶水；搬走复杂度，或加一道门禁来维持重复定义相等，都不算移除。

<a id="prove-reachability-and-the-trade-off"></a>

## 证明可达性与取舍

先用 `rg`，再读匹配结果。搜索精确符号、属性读写、判别值、事件与线协议字符串、配置键、包名，以及 `.method(` 与 `method(` 两种形式。测试与声明能展示契约，但不能证明存在已交付的生产者或消费方。

覆盖各包的源码目录、应用入口、运行时脚本、包清单与导出、加载器解析、生成的运行时资产，以及已安装包的消费方。按示例与 fixture 的实际入口分类，而不是按目录名。顺着生成的目录追到其消费方：被模型编写的插件挂载使用的目录是动态产品 API，而仅供文档的列表不是固定调用方。公开的第三方扩展路径可以是刻意的，即使仓库内零调用点。静态未使用代码检查器必须覆盖清单驱动的加载、生成产物与编译器面，而不维护一份平行的逐工作区例外清单。

对每个候选，记录当前所有者、生效的生产者/消费方路径、消失的内容、保留的内容，以及保留它的最强理由。区分：

- 移除不可达或无人读取的行为；
- 收窄公开或产品行为，并明确写出损失；
- 受保护的义务或证据不足。

当候选破坏了保留的义务、只是把同样的复杂度搬了个位置，或没有实质缩减时，否决它。按拟议改动的层级来读否决理由：一份过期的清单，或一个混合提案中被否决的那部分行为，并不裁定其中每个独立条目。重新提议前先刷新证据。小范围局部改进按紧急度规则写进可执行的 `TODO`/`FIXME`/`XXX` 注释，而不是写成独立的设计记录。

<a id="preserve-ownership-and-failure-semantics"></a>

## 保留归属与失败语义

对于复制、冻结、校验器与回调捕获，写明值的来源、下一任所有者与信任边界。同进程的有类型调用通常借用只读值；解析器、配置加载器、队列、模型/工具 JSON、持久文件、worker、进程与线协议解码器拥有或校验它们的输入。敌意 getter 或回调替换测试本身不足以确立需求。冻结根不能证明其后代不可变，id 相等也不能证明对象同一。

对于异步机制，把每个 promise、标志、取消路径、disposer 与预约映射到其所有者与状态转换。只有当多个机制表达同一事实时才能合并。在要求之处保留同步发布与回滚、回调遏制、首个终态仲裁、worker/进程归属，以及 dispose 到静默。持久的起止标记可以记录真实事实，即使记录渲染器忽略它们；丢弃被中断的工作是能力损失，不是冗余日志清理。

<a id="replace-infrastructure-only-for-a-net-reduction"></a>

## 只有净缩减时才替换基础设施

遵循依赖策略。新增包之前，先搜索既有依赖与引擎下限之上的 Node 内置模块。写明替换会删除的确切实现与专门测试、其维护与传递成本，以及胶水必须保留的每项残余行为。

演练最可能击败替换方案的那些不匹配：协议截断、取消与 teardown、配置的边界、确定性测试时钟、平台打包，以及源码入口与构建产物入口的差异。一个库覆盖了分帧，却要求为施加大小上限重建同样的分帧，就不算简化。被接受的边缘行为变化要写进提案与相关测试。不要重复证明依赖的通用规格说明，却漏掉针对本仓库专用 shim 的测试。

<a id="record-consolidate-and-validate"></a>

## 记录、合并与校验

散文在范围内时，使用 [notifyrelay-prose-standard](../notifyrelay-prose-standard/SKILL.md)。删除复述代码或属于别处所有的解释，同时保留局部行为、时序、归属与失败义务。受影响的 README、JSDoc、面向模型的目录、配置、快照与生成文件，随其归属改动一起更新。

实质性提案使用强制的记录骨架：`Problem`、`Proposal`、`Alternatives considered`、`Acceptance criteria` 与 `Risks`。包含具体消费方证据、被移除的维护成本、放弃的能力，以及可观察的验收条件。已实施的决策改用[已实施格式](../../notes/README.md#正文骨架)。决策相同时更新既有所有者的记录；不要为凑候选数量而创建重复记录。

每份新记录都要求做一次有界的取代检查：搜索覆盖同一决策或机制的旧记录，判定是完整取代还是部分取代，并按[记录规则](../../notes/README.md)处理留存、合并、三文件组删除与冻结归档。代码调研不意味着要对全仓记录做审计。保留部分取代关系，以及当前仍成立的持久、线协议、兼容性或已否决替代方案义务。

合并另一个分支时，将其独立 diff 与目标基线比较，只移植有支撑且互不重叠的提案，并合并重叠的理由。关闭另一个 PR 需要授权，或对该项清理工作有明确归属。

对于纯文档的 Agent Note 工作，运行 `pnpm run doc-sync`、`pnpm run lint` 与 `git diff --check`；对于技能或注释改动，加入适用的校验器。其他检查按受影响面选择。报告调研过的区域、有支撑的候选、有意义的否决或推迟、新增/合并/保留/移除的记录，以及实际运行过的命令。调研仍在扩张期间使用草稿 PR；不要把未经验证的搜索说成穷尽。
