# Agent Note: 核心上下文锁死锁与卡死恢复

Status: implemented

## Problem

Android 端应用进入后台再回到前台后白屏：`GuideActivity` 的首帧始终未提交，进程存活但主线程停在一个 UniFFI 方法里。现场转储显示 53 个线程中有 14 个阻塞在同一 futex 地址，锁字长恒为 `0x2`（已加锁且存在等待者），等待者覆盖主线程、发送队列、心跳、发现扫描与 tokio 运行时线程。

根因是核心上下文互斥锁 `SafeContext`（`Mutex<CoreContext>`）被持锁的阻塞调用长期占用。锁的范围覆盖了网络收发与拨号：`send_via_quic` 在锁内执行 `QuicTransport::send`，后者内部 `rt.block_on(open_bi / write_all)` 且无超时；`sender_queue::try_send` 在锁内执行 `connect`，同样 `block_on` 握手。对端进程被强杀时不会发送 FIN，触达流控上限的连接也不会推进，这些等待永不返回。而 `block_on` 需要 tokio 工作线程推进，那些工作线程自身也在等同一把锁，形成闭环。

同一条链路上还有四处同源缺口：重连线程在持有重连状态锁时反取上下文锁，与 FFI 线程的「上下文锁 → 重连状态锁」构成 ABBA；发现扫描为每台设备重复取上下文锁；音频控制帧在锁内发送；mDNS 电量重注册在锁内执行。

次要故障被放大成主因：设备离线时发送队列每次都重拨、每次失败都记警告，一台不可达设备在日志里累计 365 次连续失败，持续把发送线程推进上述阻塞路径。

## Decision

**锁只保护内存。** 上下文锁内只取句柄与读写字段，网络收发、拨号、mDNS 重注册、线程 `join` 全部移到锁外。`send_via_quic` 与 `send_control_via` 接收传输层句柄而非上下文引用；`sender_queue::try_send` 在锁内取 `Arc<QuicTransport>` 与在线状态，锁外发送与重连。

**阻塞调用一律有界。** `QuicTransport::send` 与 `connect` 分别以 `tokio::time::timeout` 限制在 5s 与 8s，超时按失败返回。

**锁序固定为「上下文锁 → 组件锁」。** 重连线程先在本机一次取锁中读出自机 uuid 与在线集合，再进入重连状态锁；发现扫描每轮只取一次本机身份，不再逐设备取锁。

**离线不是故障。** 发送队列先按心跳在线窗口判定，在线才直接发送；离线或会话失效时按已知地址重连一次，失败记 `info` 并按退避重试。只有已在线却发送失败才记 `warn`。`try_send` 返回 `Sent` / `Offline` / `Failed` 三态，让日志级别与重试策略按状态分派。

**关停与上下文锁解耦。** 新增 `lifecycle` 模块持有进程级原子信号。`Core::request_shutdown` 只置位该信号，不取上下文锁，因此在锁被卡住时依然立即返回；发送队列、心跳、发现扫描、重连、状态合并五个后台循环在每轮入口检查该信号并退出。协调线程在有界等待（3s）内取锁并释放 mDNS 句柄与 QUIC 传输层，取不到即放弃，不重试、不阻塞。

**平台侧看门狗只做统计与请求。** `CoreWatchdog` 位于 commonMain，用原子计数统计核心调用在途数量，存在未返回调用超过 10s 时调用 `NativeCore.requestShutdown()`。它不进入核心锁、不捕获异常、不改变返回值，因此不会成为新的死锁参与者。恢复依赖 `NativeCore.createContext()` 重建实例：Rust 侧 `create_context` 清除关停信号，Kotlin 侧在创建新 `Core` 后调用 `CoreWatchdog.reset()`。

## Alternatives considered

**给上下文锁换 `try_lock` 加重试。** 只把死锁从「永久等待」变成「反复失败」，持锁方仍在阻塞，调用方拿不到任何进展；而且大量调用点原本就需要等待完成，改成失败语义会把正确性负担推给每个调用者。

**用 `parking_lot` 的 `try_lock_for` 做有界等待。** 与上一项同一缺陷：有界等待改变的是等待者的行为，不改变持锁者不释放的事实。真正的修复是把阻塞排除在锁外。

**在 Rust 侧用独立看门狗线程检测并强拆锁。** 拆别人的 `MutexGuard` 意味着继续在未定义的状态上运行：被中断的调用可能已写入一半数据，`Arc` 与句柄的生命周期也无法保证。放弃的是「原地恢复」，换来的是不引入未定义行为。

**关停信号放在上下文里（新增 `CoreContext` 字段）。** 读该字段同样需要上下文锁，恰好在最需要它的场景不可用。信号必须独立于被它保护的对象。

**看门狗把每次调用放到工作线程并超时丢弃。** 超时线程仍在 native 里持锁运行，问题不变，还多出一层线程管理与结果不确定的语义。

**离线也记警告。** 设备离线是桌面对端关机、手机锁屏的常态，不是故障；把常态记成警告会淹没真正的失败，并且在本仓库的日志分流下形成可观测性噪声。

## Consequences

锁内不再有阻塞调用后，单个调用阻塞不再拖住整条核心链路：发送超时只影响该次发送，其余调用照常推进。

代价是发送失败与建连失败各自有 5s / 8s 的上限，设备确实不可达时一次发送最多占用约 13s 的发送线程时间。发送队列的并发上限（5）与设备退避（递增至 5s）把这部分开销限在固定线程内，不扩散到调用方。

关停信号是进程级的，不随上下文重建自动清除，因此 `create_context` 必须显式清除；否则新实例启动即处于关停状态。

关停只是让线程退出，不回收旧上下文（其内存在进程生命周期内不释放，这与既有设计一致）。反复触发看门狗会让旧上下文与已退出线程的资源累积，但这是恢复路径的极端情形，优于进程永久卡死。

看门狗阈值 10s 短于单次核心调用的最坏耗时（一次锁外发送加一次重连约 13s），因此极端网络下看门狗可能先于调用返回触发关停。此处取保守方向：误触发只重启核心，漏触发会让进程永久卡死。阈值以常量形式集中，按现场数据调整。

## Testing

`cargo test --lib` 覆盖发送队列三态（`try_send_reports_offline_without_transport`、`try_send_delivers_over_quic_session`）与关停信号幂等（`shutdown_signal_is_global_and_idempotent`）。`:core:compileAndroidMain` 与 `ktlintFormat` 验证绑定重生成后的 Kotlin 侧可编译。
