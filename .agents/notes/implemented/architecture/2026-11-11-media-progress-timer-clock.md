# Agent Note: 媒体进度按计时器口径由接收端推算

Status: implemented

## Problem

媒体卡此前只有标题与艺术家：桌面端从 SMTC 取到播放位置与总时长，但只用于本机叠加层，远端回推的会话没有进度字段；安卓端读得到 `MediaController` 的位置，却只喂给歌词字段判定，既不显示也不上报。两端各自看到的是「谁在放什么」，看不到放到哪。

进度不能按帧推送。播放位置每时每刻都在变，若它参与状态合并的差异判定，6 秒一轮的心跳查询会把每一次查询都判成「有变更」，通道被位置更新占满，封面等大字段的带宽会被重复消耗。

## Decision

媒体报文增加四个进度字段，口径与超级岛计时器组件（`TimerInfo`）同构：`timerWhen` 为位置归零时刻、`timerTotal` 为总时长、`timerSystemCurrent` 为采样时刻、`timerType` 取 1 播放 / 2 暂停。Rust 的 `parse_media_inbound` 一并归一，发送端可直接给计时器字段，也可只给 `positionMs`/`durationMs`/`positionAt` 由归一化换算出等价口径。

进度由接收端按本地时钟推算，不随报文逐帧到达：播放中取「采样位置 + 经过时间」，暂停停在采样位置，两者都截到总时长。推算实现收敛在 `:base` 的 `PlaybackProgress`，`MediaSessionSnapshot` 与 `MediaSessionData` 都委托它，界面每秒重算一次。

上报触发只有两类：换曲（标题、艺术家或总时长变化）与固定周期。固定周期沿用既有节奏——安卓走 Rust 媒体心跳（6 秒）与状态查询回调，桌面端由 `DesktopMediaControlPort` 每秒轮询 SMTC、每 6 秒或换曲时推送。播放态翻转另算一次变更：暂停与恢复必须传播，否则接收端会继续按旧基准推进。

桌面端补齐了此前缺失的上报链路：本机会话经 `DATA_MEDIAPLAY` 推给在线设备，与安卓同一条通道、同一个合并引擎。接收侧在报文入口按「接收媒体消息」三档判定，仅音频档要求正在接收音频；上报受「发送媒体通知到它端」开关控制。

## Alternatives considered

**按进度变化推送，接收端直接显示报文值。** 界面在两次推送之间静止，进度条只能整段跳变；要平滑就得把推送周期压到秒级，等于让位置更新独占状态通道，与关闭封面等大字段的差异合并收益相抵。

**只在接收端推算，报文不带采样时刻。** 接收端只能从「收到的时刻」起算，而收到时刻落后于采样时刻，长曲目会累计固定偏差；报文带上采样时刻让两端共用同一个基准。

**复用 `positionMs`/`durationMs`/`positionAt` 作为唯一口径。** 这套字段语义清楚，但与超级岛的计时器组件是两套表达，接收端要写两次推算。取计时器口径后两端共用一个 `formatTimerInfo` 与一套推算规则；Rust 归一仍接受位置形式，兼容未升级的发送端。

**让 `parse_media_inbound` 之外的平台侧各自解析进度。** 归一化分叉两份，两端会各自漂移；进度字段放进归一结构后，安卓与桌面拿到的是同一份口径。

**把进度写进 `param_v2`。** 超级岛的进度组件是另一种视觉（多节点进度条），与媒体卡的细进度条不是同一形态；写进参数区还需要每次进度推进都重建报文。

## Consequences

进度精度取决于对端时钟与本机时钟的偏差：两边系统时间不同步时，第一次收到的位置会整体偏移，之后按本地时钟匀速推进，偏移不再变化。SMTC 与 `MediaController` 给出的位置本身是「上次上报值」，播放中不回读真实播放头，因此秒级误差仍可能存在。

暂停与恢复、换曲会重置基准；拖动进度条只在标题或艺术家变化时被感知，纯 seek 不会立刻同步到对端，最迟在下一个固定周期生效。

core 版本只升 patch：新增字段是可选扩展，缺失按 0 处理、未知键被忽略，`major.minor` 不变，AAD 与协议兼容判定都不受影响，新旧端保持互通。

桌面端「胶囊歌词」开关仍无对应实现：桌面端没有本机胶囊渲染链路，该开关只在安卓端生效。
