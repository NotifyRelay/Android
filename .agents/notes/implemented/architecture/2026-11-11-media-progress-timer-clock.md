# Agent Note: 媒体进度按计时器口径由接收端推算

Status: implemented

## Problem

媒体卡此前只有标题与艺术家：桌面端从 SMTC 取到播放位置与总时长，但只用于本机叠加层，远端回推的会话没有进度字段；安卓端读得到 `MediaController` 的位置，却只喂给歌词字段判定，既不显示也不上报。两端各自看到的是「谁在放什么」，看不到放到哪。

进度不能按帧推送。播放位置每时每刻都在变，若它参与状态合并的差异判定，6 秒一轮的心跳查询会把每一次查询都判成「有变更」，通道被位置更新占满，封面等大字段的带宽会被重复消耗。

## Decision

媒体报文增加四个进度字段，口径与超级岛计时器组件（`TimerInfo`）同构：`timerWhen` 为位置归零时刻、`timerTotal` 为总时长、`timerSystemCurrent` 为采样时刻、`timerType` 取 1 播放 / 2 暂停。Rust 的 `parse_media_inbound` 一并归一，发送端可直接给计时器字段，也可只给 `positionMs`/`durationMs`/`positionAt` 由归一化换算出等价口径。

进度由接收端按本地时钟推算，不随报文逐帧到达：播放中取「采样位置 + 经过时间」，暂停停在采样位置，两者都截到总时长。推算实现收敛在 `:base` 的 `PlaybackProgress`，`MediaSessionSnapshot` 与 `MediaSessionData` 都委托它，界面每秒重算一次。

基准换算取自历史实现的 `ApplyTimerBase`，提取为 `:base` 的 `TimerClock.rebase`：对端的「归零时刻」与「采样时刻」都是对端时钟，只有两者的差值是与时钟原点无关的已计时长；接收端以本地采样时刻重算归零时刻。直接拿对端时间戳当基准会把两端时钟偏差算进进度，表现为播放中偏大、暂停时回落到真实值。超级岛的 `formatTimerInfo` 与安卓、桌面两个媒体接收端都调用这一个函数，不再各写一份换算。远端超级岛的换算统一用「内容在本地被接收的时刻」：安卓侧由 `SuperIslandSourceStore` 在内容入库时登记，浮窗经 `LocalSuperIslandReceivedAtMs` 下发，系统通知复刻的 chronometer 与胶囊文本也从同一登记值换算；桌面上报条目的 `updatedAt` 即接收时刻。本地内容的接收时刻与采样时刻同钟，换算退化为恒等。

报文里的位置必须是「推送时刻的位置」。平台给的播放位置多是快照（安卓 `PlaybackState.position`、桌面 SMTC `TimelineProperties.Position`），只在状态变更时刷新；把它配推送时刻会让接收端每轮重算基准都退回旧位置，表现为进度涨到某处又回落。发送端因此在推送时刻把位置推进到此刻，实现在 `:base` 的 `PlaybackPosition`：能拿到快照时刻与速率的用 `predict`（安卓由 `PlaybackStatePosition` 把 `lastPositionUpdateTime` 换算到 epoch 后调用），只能轮询读数的用 `PlaybackPositionTracker`（读数变化处建基准，未变化时按经过时间推进，桌面 SMTC 即如此）。

上报触发只有两类：换曲与固定周期。换曲的判定口径见[单曲识别下沉到公共端并随报文携带歌曲身份](2026-11-13-shared-song-recognition.md)，不用标题。固定周期沿用既有节奏——安卓走 Rust 媒体心跳（6 秒）与状态查询回调，桌面端由 `DesktopMediaControlPort` 每秒轮询 SMTC、每 6 秒或换曲时推送。播放态翻转另算一次变更：暂停与恢复必须传播，否则接收端会继续按旧基准推进；安卓的去重键因此把 `PlaybackState.state` 纳入，状态变化即触发一次上报，两条上报路径都在推送时现取位置、播放态与时长。

桌面端补齐了此前缺失的上报链路：本机会话经 `DATA_MEDIAPLAY` 推给在线设备，与安卓同一条通道、同一个合并引擎。接收侧在报文入口按「接收媒体消息」三档判定，仅音频档要求正在接收音频；上报受「发送媒体通知到它端」开关控制。

## Alternatives considered

**按进度变化推送，接收端直接显示报文值。** 界面在两次推送之间静止，进度条只能整段跳变；要平滑就得把推送周期压到秒级，等于让位置更新独占状态通道，与关闭封面等大字段的差异合并收益相抵。

**只在接收端推算，报文不带采样时刻。** 接收端只能从「收到的时刻」起算，而收到时刻落后于采样时刻，长曲目会累计固定偏差；报文带上采样时刻让两端共用同一个基准。

**复用 `positionMs`/`durationMs`/`positionAt` 作为唯一口径。** 这套字段语义清楚，但与超级岛的计时器组件是两套表达，接收端要写两次推算。取计时器口径后两端共用一个 `formatTimerInfo` 与一套推算规则；Rust 归一仍接受位置形式，兼容未升级的发送端。

**让 `parse_media_inbound` 之外的平台侧各自解析进度。** 归一化分叉两份，两端会各自漂移；进度字段放进归一结构后，安卓与桌面拿到的是同一份口径。

**把进度写进 `param_v2`。** 超级岛的进度组件是另一种视觉（多节点进度条），与媒体卡的细进度条不是同一形态；写进参数区还需要每次进度推进都重建报文。

## Consequences

进度与计时显示不再受两端时钟偏差影响：基准换算只用对端两个时间戳的差值，偏差被消掉。安卓系统通知复刻走 `Notification.setWhen` 与 chronometer，换算后同一条内容无论浮窗还是通知通道显示一致。仍存在的误差来自报文的传输时延（基准取接收时刻，晚到即略微偏大）以及数据源本身——SMTC 与 `MediaController` 给出的位置是「上次上报值」，播放中不回读真实播放头，秒级误差仍然存在。

暂停与恢复、换曲会重置基准；拖动进度条只在标题或艺术家变化时被感知，纯 seek 不会立刻同步到对端，最迟在下一个固定周期生效。

推算时钟的记忆键取采样相关的标量而非会话对象：宿主的媒体卡随帧重组，会话对象逐帧重建且默认时间戳不同，以对象为键会让时钟每帧重启，进度在采样值与当前时刻之间反复跳动。已有帧时钟的宿主（桌面叠加层）直接把帧时刻传入，展开态与收起态因此共用同一根时钟。

core 版本只升 patch：新增字段是可选扩展，缺失按 0 处理、未知键被忽略，`major.minor` 不变，AAD 与协议兼容判定都不受影响，新旧端保持互通。

桌面端「胶囊歌词」开关仍无对应实现：桌面端没有本机胶囊渲染链路，该开关只在安卓端生效。
